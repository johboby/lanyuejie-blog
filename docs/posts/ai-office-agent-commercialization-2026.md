2026 年 AI 办公 Agent 最大的变化，不是能力变强了（那件事在 2025 年就已经发生了），而是**计费模式正在变**。

过去两年，AI 办公产品的定价逻辑是"按 Token 收费"或"按席位收费"，客户为"调用量"或"人头数"付费。2026 年出现了一批"按任务完成结果收费"的产品：客户为"报告交付了"、"代码通过了"、"发票录入完成了"付费，而不是为"Agent 跑了多少轮"付费。

这个转变的技术结构、商业逻辑，以及它对行业格局的影响，是这篇文章要讲清楚的。

## 计费模式转变的技术前提

"按结果收费"不是凭空出现的，它有三个技术前提在 2025-2026 年同时成熟了。

**前提一：MCP（Model Context Protocol）生态标准化。** MCP 是 Anthropic 在 2024 年底提出的开放协议，2025 年被广泛采纳。它解决的问题是：Agent 如何调用外部工具。在 MCP 之前，每个 Agent 产品要对接每个 SaaS 工具，需要写一遍集成代码；MCP 把"工具调用"标准化了，Agent 只需要实现 MCP client，工具方只需要发布 MCP server，互不依赖。

到 2026 年，主流办公工具（Google Workspace、Microsoft 365、Slack、Jira、Notion、Salesforce）都有了官方或社区 MCP server。这意味着一个 Agent 产品不需要自己写 20 个工具的集成，而是通过 MCP 协议自动发现可用工具。这大幅降低了"按结果收费"的实现成本——工具调用链路是标准的，出错率是可预期的，"结果"的边界是清晰的。

**前提二：A2A（Agent-to-Agent）协议让 Agent 之间可以协作。** A2A 协议（Google 主导，2025 年发布）解决的问题是：多个 Agent 如何相互发现、通信、协商。在 A2A 之前，"写代码的 Agent"和"做测试的 Agent"是两个孤立系统；A2A 让它们可以像微服务一样相互调用。

对"按结果收费"的含义是：一个"任务"可以拆成多个 Agent 协作完成，每个 Agent 的"结果"是中间产物，最终"结果"是任务交付物。计费边界从"单 Agent 调用"变成了"任务交付"，这比"按 Token"或"按席位"更贴近客户真正在乎的东西。

**前提三：推理成本降到可以支撑"多轮工具调用"。** 2026 年推理成本较 2024 年下降了约 10 倍（具体降幅因模型而异），让"一个任务跑 50-100 轮工具调用"在经济学上变得可行。在此之前，"多轮调用"的成本高于"结果"的价值，"按结果收费"在经济上不成立。

## 三种商业化路径

2026 年 AI 办公 Agent 的商业化，实际上有三条并行的路径，对应三种不同的客户画像。

### 路径一：垂直场景 SaaS（"报告生成"、"发票处理"、"客户跟进"）

**代表产品：** Glean（企业知识搜索+Agent）、11x.ai（销售 SDR Agent）、Artisan（AI 销售助理）、Clay（数据富集+销售外联 Agent）

**商业逻辑：** 把 Agent 嵌入一个明确的工作流（比如"销售外联"），按"完成的合格任务数"收费，而不是按"Agent 调用次数"收费。客户买的是"销售线索"，不是"AI 调用"。

**2026 年的特征：** 这条路径的客户决策者是企业业务负责人（不是技术负责人），定价锚点是"人工成本"而不是"技术成本"。一个"合格销售线索"的人工成本是 50-100 美元，Agent 按 5-15 美元/合格线索收费，ROI 清晰可算。这是"按结果收费"最成熟的形态。

**关键约束：** 垂直场景 SaaS 的护城河不是 Agent 能力，而是"数据接入 + 行业 Know-how"。谁的 MCP 工具链覆盖更广、行业数据标注更细，谁的"合格任务"定义就越清晰，越能支撑"按结果"的定价。

### 路径二：企业级 Agent 平台（"内部 AI 员工"）

**代表产品：** 中科创达 TurboX、百度智能云 Agent 平台、阿里云百炼、Microsoft Copilot Studio（Agent 版）

**商业逻辑：** 给企业提供一套 Agent 基础设施（模型路由 + 工具管理 + 权限审批 + 任务监控），企业按"部署的 Agent 实例数"或"月度 Token 消耗"付费，而不是按"单个任务结果"付费。

**2026 年的特征：** 这条路径的客户决策者是企业 IT 负责人，定价锚点是"IT 基础设施成本"而不是"业务结果"。核心卖点是"可控"——Agent 执行哪些任务、能访问哪些数据、出错后如何回滚，都要在平台层统一管理。

**关键约束：** 企业级平台的"按结果收费"比垂直 SaaS 难一个量级，因为企业任务的边界是模糊的（"帮我跟进这个项目"到底意味着什么"结果"？）。所以企业级平台目前仍以"按 Token/按席位"为主，"按结果"是未来的方向而不是现在的现实。

### 路径三：开发者 Agent 工具链（"Copilot + Agent"）

**代表产品：** GitHub Copilot（Agent 模式）、Cursor、Devin（Cognition）、Claude Code、Trae（字节跳动）

**商业逻辑：** 给开发者提供"从需求到代码"的完整 Agent 能力，按"席位"或"算力消耗"收费。客户买的是"开发速度"，定价锚点是"工程师人力成本"。

**2026 年的特征：** 这条路径的"按结果收费"最接近实现——"结果"是"代码合并了"或"测试通过了"，边界清晰。Cursor 已经在探索"按任务完成"的计费模式，Claude Code 在 2026 年引入了"按 commit 计费"的试验。

**关键约束：** 开发者工具链的"结果"定义比销售场景复杂——"代码合并不代表功能正确"，"测试通过不代表没有 bug"。"按结果收费"在开发工具里的真正"结果"应该是"生产环境无故障"，这个边界目前还无法精确测量。

## 一个被忽略的细节：MCP 的"发现"问题

MCP 协议解决了"工具调用"的标准化，但还没有解决"工具发现"的问题。

目前 MCP 工具的发现主要靠三种方式：硬编码列表、MCP Registry（社区维护）、AI 语义搜索。三种方式都有明显缺陷：硬编码需要人工维护，Registry 的质量参差不齐，语义搜索的召回率不够高。

2026 年下半年开始出现"Agent 自主发现工具"的趋势——Agent 自己判断需要哪些工具，通过 MCP Registry 或语义搜索找到对应 server，然后动态注册。这个趋势如果跑通，"按结果收费"的"结果"边界会从"预设任务"扩展到"开放任务"，商业模式会发生质变。

## 对开发者和企业采购方的实操建议

**对做 AI 办公 Agent 产品的团队：**

1. **尽早确定"结果"的定义，并把它写进定价模型。** "合格任务"的定义越清晰，越能支撑"按结果收费"。模糊的"结果"只能按 Token 收费，而 Token 计费在 2026 年的价格战中越来越难盈利。

2. **把 MCP 工具链作为核心竞争力，而不是把模型能力作为核心竞争力。** 2026 年模型能力的差距在缩小，工具链的广度和质量才是"合格任务"定义能力的来源。

3. **企业级产品先做"可控"，再做"智能"。** 企业采购方的第一诉求是"知道 Agent 在做什么"，不是"Agent 多聪明"。权限审批、任务日志、可撤销操作，这些"控制层"能力是 2026 年企业级 Agent 的标配。

**对企业采购方：**

1. **"按结果收费"目前只在垂直场景 SaaS 里真正成立。** 在"销售外联"、"发票处理"、"客服工单"这三个场景里，"合格任务"定义清晰，ROI 可算，建议优先试点。

2. **企业级 Agent 平台目前仍应按"基础设施成本"采购，不要期望"按结果"计费。** 平台层的能力是"可控"，"结果"要等业务场景层才能定义。把"按结果收费"的期望放到平台采购里，会买不到想要的东西。

3. **开发工具链的"按 commit/按任务"计费，要算清楚"生产故障成本"。** 如果"按任务计费"的 Agent 代码上线后产生生产故障，故障成本远超任务费用。在采用这类计费模式前，把"故障成本"算进 ROI 模型。

## 写在最后

2026 年 AI 办公 Agent 的商业化，处在一个"能力已经够用，计费模式正在切换"的窗口期。"按结果收费"不是一个营销话术，而是一个有明确技术前提（MCP + A2A + 推理成本下降）和商业逻辑（ROI 锚定人工成本）的结构性转变。

三条路径中，垂直场景 SaaS 是"按结果收费"最成熟的形态，企业级平台是"可控"需求最迫切的形态，开发者工具链是"结果定义"最复杂也最接近突破的形态。三条路径会在 2027 年继续分叉，共同构成"AI 办公 Agent"的完整商业图景。
