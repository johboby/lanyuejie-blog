我先说结论。

2026 年 4 月 24 日，DeepSeek 发布 V4 预览版，同步开源，核心主张是——**"迈入百万上下文普惠时代"**。同一天，DeepSeek API 上线 V4-Pro 与 V4-Flash 两个版本，旧的 `deepseek-chat` 与 `deepseek-reasoner` 接口将于 2026-07-24 停止使用。

**这三件事里，最重要的一件事不是"DeepSeek 又发布了新模型"，是"百万上下文"从 2024-2025 年的差异化能力，变成了 2026 年的行业标配**。

## "百万上下文"这个词的重量

回到 2024 年初，"百万上下文"这个数字还是一个营销词。

Gemini 1.5 Pro 是第一个公开宣称 1M token 上下文窗口的商用模型（2024-02）。当时行业对它的反应是半信半疑——**"窗口大"和"能用"是两件事**。窗口扩到 100 万 token 之后，模型能不能真的把 100 万个 token 里的信息"记住"、能不能对第 80 万个 token 做精确引用，都是未知的。

2024 年到 2025 年之间，行业做了大量"长上下文可用性"的研究——

- Google 在 Gemini 1.5 Pro 上做了 LongBench、RULER 等基准测试
- Mistral 推出了 Mistral Large 2412 的 128K 上下文版本
- OpenAI 在 GPT-4 Turbo 上把上下文从 128K 扩到 128K（这个"扩容"看起来没变，但内部的注意力架构做了重写）
- Anthropic 在 Claude 3.5 上做到 200K，2025 年在 Claude 4 上做到 500K

**每一次扩容都在回答同一个问题——"模型能不能真的用")**。

答案是——**不能，但能"用得越来越像"**。

## DeepSeek V4 的"普惠"是什么意思

DeepSeek 在 V4 发布时的措辞有一个词值得单独看——**"普惠"**。

DeepSeek 官方公告的原话是——

> 今天，我们全新系列模型 DeepSeek-V4 的预览版本正式上线并同步开源。DeepSeek-V4 迈入百万上下文普惠时代。

**"普惠"这个词的隐含意思是——百万上下文不再是"贵价产品"，而是"标准配置"**。

这个说法在 2026 年 4 月有非常具体的产业含义——**DeepSeek 把百万上下文的 API 单价压到了同行 1/5 到 1/8 的水平**。

原因还是 DeepSeek 过去两年已经在 R1、R2 上打磨过的稀疏注意力、MoE、量化推理这一整套工程能力。**V4 是这套工程能力第一次完整应用到一个"1M 上下文"的产品上**。

## 从"差异化"到"标配"：产品设计的连锁反应

**当百万上下文变成标配，大模型产品的整个设计逻辑都要重写**。

我先列几个具体变化——

**变化一：RAG 从"必需品"变成"可选件"**

过去两年，RAG（Retrieval-Augmented Generation）几乎是企业级大模型应用的标准架构。原因是——上下文窗口不够大，一次塞不下用户的全部文档，必须先检索，再喂给模型。

**当百万上下文变成标配，RAG 的定位从"必需品"变成了"性能优化项"**——

- 对于小型企业（几万份文档），可以直接把全部文档塞进上下文
- 对于中大型企业（上百万份文档），RAG 依然是必要的
- 但对于"个人用户+ 单一大文档"这个场景，RAG 变得完全多余

**RAG 不是死了，是从"基础设施"降级成了"可选优化"**。

**变化二：从"检索-生成"到"直喂-理解"的产品架构重写**

Cursor、Windsurf、Claude Code、Trae、CodeBuddy 这些 agentic coding 工具，过去两年都在做一件事——**把整个代码仓库直接喂给模型**。

Cursor 的 "Codebase Indexing"、Claude Code 的 "Repo-wide Context"、Trae 的 "Full Codebase Understanding"——这些功能的共同逻辑是——**不再做局部 RAG，而是把整个代码库打包成一个大上下文塞给模型**。

**这套架构在过去两年成本太高，2026 年之后成本可行了**。

**变化三：从"聊天窗口"到"工作空间"的产品形态迁移**

百万上下文意味着——**用户可以在一次对话里塞入 100 万字**。

这个能力对应的产品形态是——**从"聊天窗口"变成"工作空间"**。

用户不再是"问一个问题、得到一段回答"，而是——"把整个项目文档、整个代码库、整个数据表、整个视频转写稿——全部塞进去，让模型在里面工作"。

**Cursor 的 2026 年 iOS 移动端支持、Claude Code 的 "Remote Agent"、Trae 的 "Long-horizon Task"——都是这个新形态的产品化表达**。

## 关于 API 版本切换的时间线

DeepSeek 在 2026-04-24 的 API 公告里有一句话——

> 请大家注意：旧有的 API 接口的两个模型名 `deepseek-chat` 与 `deepseek-reasoner` 将于三个月后（2026-07-24）停止使用。

**这句话的深意是——DeepSeek 用 3 个月的过渡期，把 API 版本切换到 V4-Pro / V4-Flash**。

这个"3 个月过渡期"在行业里非常罕见——大多数大模型公司在切换主 API 时只给 30-60 天过渡期，DeepSeek 给了 90 天。**这个时间长度背后是一个商业判断——DeepSeek 知道切换会破坏用户，愿意用更长的过渡期换取用户信任**。

**"用 3 个月的过渡期换用户信任"这个判断，是过去两年中国大模型行业里最稀缺的产品价值观之一**。

## 一个更深的观察

V4 的发布，我读到的是另一层意思。

**DeepSeek V4 的"百万上下文普惠"不是一个技术突破，是一次商业模式的公开表态**。

它的技术突破在 R1、R2 时已经做完了——稀疏注意力、MoE、量化推理、KV cache 优化，这套东西在 V4 上是完整应用，不是首次出现。

**V4 真正做的事情是——"把 1M 上下文从"贵价产品"变成"标准配置"这个商业判断**。

这个判断在 2026 年 4 月做出，意味着 DeepSeek 已经意识到——**大模型行业的"差异化竞争"正在从"模型能力"转向"单位算力成本"**。

**能力不再是壁垒，成本是壁垒**。这个转变，是过去两年中国大模型行业最重要的行业演化。

## 关于"百万上下文"和"1M token"的关系

最后一个技术细节值得单独说——**"1M token"到底意味着什么**。

- 1M token ≈ 150 万英文单词 ≈ 一份 5000 页的 PDF
- 1M token ≈ 3 万行代码
- 1M token ≈ 一个中等规模的企业级代码仓库
- 1M token ≈ 4 小时的会议录音转写

**这些数字加在一起，意味着——"1M 上下文"这个能力，让大模型第一次具备了"处理整个知识工作"的能力**。

**它不再是"帮你写一段代码"的工具，是"帮你处理整个项目"的伙伴**。

## 写在最后

2026 年 4 月 24 日 DeepSeek V4 发布时，我在读官方公告的时候，第一反应是——"百万上下文终于来了"。

三个月后，也就是 2026 年 11 月的今天，我回头看，发现一个更清晰的判断——

**"百万上下文"这个能力，在 2026 年已经不再是差异化，而是入场券**。

**入场券意味着——你必须具备，但不加分**。

DeepSeek 在 4 月做出这个判断时，其实是在告诉整个行业——**"百万上下文"从今天开始是标配，我们把它做出来，你要么跟上、要么被淘汰**。

**这个信号比 V4 本身的性能数字重要得多**。

它意味着——**中国大模型行业正在从"能力竞赛"进入"成本竞赛"阶段**。这个阶段的赢家，不是最强的模型，是"用最便宜的算力做到最强能力"的那一家。

**过去十年中国科技行业的每一次产业演化，都是这样发生的**。
